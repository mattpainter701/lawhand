# Core UX ordered sprint execution plan

Companion to the [core UX epic](./core-ux-future-state-epic-2026-09-22.md). The epic holds scope, estimates and acceptance criteria; this document holds implementation order, prerequisites and evidence.

---

This is the task-level execution plan for the [epic](./core-ux-future-state-epic-2026-09-22.md)'s UX stories. All checkboxes are **planned, not completed**. The hierarchy is epic → phase gate → sprint → numbered task → implementation PR/evidence. UX-xx remains the scope/estimate identifier; Sx.yy identifies an executable task. The story table defines the outcome, this section defines implementation order, and [Usability validation](./core-ux-future-state-epic-2026-09-22.md#usability-validation) remains the only source of scenario thresholds.

**Default sequence: S1 → S2 → S3 → S4 → S5 → S6 → core acceptance; then S7 → S8 only if Phase D is selected.** Tasks inside each sprint run in numbered order unless explicitly described as independent preparation. A completed prerequisite means its contract is agreed and, when code is required downstream, its implementation is merged, available in the integration environment, and verified at the recorded SHA. A draft PR or an unmerged endpoint is not a completed dependency.

Proposed cadence is two-week planning/review timeboxes once the team is staffed. The table allocates ordered scope, not eight guaranteed calendar dates: split a sprint if available capacity cannot accommodate its tested scope; keep its dependency order and do not advance an incomplete gate because the timebox ended. Engineer-days are summed effort across contributors, not elapsed days. Before Sprint 1, name the people filling FE-A (matters/CRM/navigation), FE-B (tasks/calendar), BE (API/access/data), product/UX and QA roles. One person can fill several roles; do not assume three engineers are available. Dates, velocity and concurrent capacity remain uncommitted.

## Release checklist applied to each implementation slice

These repeatable gates are work within the relevant implementation story and shared UX-09 allocation, not eight extra budgets. Product/UX owns usability acceptance, each implementer owns focused tests, QA owns independent checks, and the designated release owner owns any authorized deployment.

- [ ] **R.01 — Ready to implement:** record task/story IDs, predecessor contract/SHA, named owner, current-main starting SHA, isolated branch/worktree, shared-file ownership and the demonstrated failure/outcome. Resolve affected policy decisions before dependent edits.
- [ ] **R.02 — Ready for review:** finish behavior and focused tests, real API/database checks where data/access is involved, keyboard/zoom/narrow-viewport checks, and empty/dense/failed/restricted states relevant to the slice. Record evidence against the task IDs and canonical scenarios.
- [ ] **R.03 — Ready to merge:** semantically update against current main; inspect the final diff, migrations if any, required documentation and correctly sequenced release notes. Complete the PR attestations, push, and wait for all required CI and the merge gate on the final head. Shared owners review changed interface contracts.

- [ ] **R.05 — Ready to expand:** record canonical scenario results and related regression results. Any wrong matter/deadline, unintended send, lost input, duplicate committed action or access leak blocks rollout. Resolve the failure or explicitly withhold the affected feature; averages do not waive these failures.

Verify release acceptance where deployment is authorized, then retire only the completed clean worktree under repository policy.
